-------------------------------------------------------------------------------
VERDICT - NOT READY TO DEPLOY
-------------------------------------------------------------------------------

The application itself is in good shape. The build is green, all 58 routes pass
structural QA, every internal link resolves, and SEO is complete.

What blocks a deploy is not code quality. It is one live brand-damaging content
defect, a framework with an unpatched RCE advisory that this config activates,
and the fact that none of the work exists anywhere but one disk.

Two of the four blockers already affect the live site. They do not require a
deploy to fix - they require a decision.

-------------------------------------------------------------------------------
B1  21 of 34 project photographs carry a third-party trial watermark
    [LIVE NOW]  [CONTENT]
-------------------------------------------------------------------------------

A banner reading "Protected with trial version of Visual Watermark. Full
version doesn't put this mark." runs along the bottom edge of 21 of the 34
photographs the site displays. This is on the live site today, on the detail
pages of the studio's flagship work.

    watermarked ................................... 21 / 34
    clean ......................................... 13 / 34
    clean originals recoverable from archive ......  3
    unrecoverable - owner's originals required .... 18

Determined two ways: visual inspection of the bottom strip of all 34 files, and
a horizontal-gradient detector that separated 19 of 21 cleanly with no false
negatives. The two it missed were confirmed at full resolution.

The companion sanity-project-manifest.csv originally recorded this as 26 stamped
/ 8 clean and named the wrong files - 7 of the 8 it called clean are stamped.
That has been corrected. Acting on the original list would have re-shot
photographs that were already fine.

FIX: three files can be swapped from the recovered archive immediately. The
other 18 need the owner's pre-watermark originals - they exist in no repository,
archive, or git revision.


-------------------------------------------------------------------------------
B2  Next.js 16.2.4 is inside the vulnerable range, and AVIF is enabled
    [LIVE NOW]  [SECURITY]
-------------------------------------------------------------------------------

npm audit reports 3 production vulnerabilities, one critical. The affected range
is 9.3.4-canary.0 - 16.3.2; the installed version is 16.2.4.

    GHSA-2xp9-vwfh-vxw4  RCE in Image Optimization API when AVIF is used
    GHSA-c4j6-fc7j-m34r  SSRF via WebSocket upgrades            CVSS 8.6
    GHSA-492v-c6pp-mqqv  Middleware bypass, route param injection  CVSS 8.1
    GHSA-h64f-5h5j-jqjh  DoS in Image Optimization API           CVSS 5.9

The first matters most here because it is not hypothetical for this config:
next.config.mjs sets formats: ["image/avif", "image/webp"], so the AVIF path is
active on every optimized image on the site.

NOT APPLICABLE: the CVSS 9.0 advisory in this set is an unauthenticated RCE on
Windows-hosted servers. Deployment is Ubuntu, so that one does not apply - worth
stating plainly, because the headline "critical" severity comes largely from it.

Also flagged by npm audit (both high, both build-time rather than request-path):
    postcss  <= 8.5.22        arbitrary .map file read via sourceMappingURL
    sharp    <= 0.35.4-rc.0   inherited libvips / libheif CVEs

FIX: upgrade to next@16.3.4 (latest; first patched release is 16.3.3). A minor
move within 16.x, but the build is the only gate this project has - re-run the
full 58-route sweep afterwards.

Every change made across this and previous sessions exists only as modified

    modified .... 168

HIGH
===============================================================================

-------------------------------------------------------------------------------
H1  No security headers are set by the application
    [LIVE NOW]  [SECURITY]
-------------------------------------------------------------------------------

next.config.mjs has no headers() block at all. Its only keys are images and
redirects. Nothing sets Content-Security-Policy, Strict-Transport-Security,
X-Frame-Options, X-Content-Type-Options or Referrer-Policy, and poweredByHeader
is not disabled, so every response advertises X-Powered-By: Next.js.

These may be set in nginx instead. That config is on the server and outside this
repository, so this audit CANNOT confirm either way.

    ==> CHECK THE NGINX CONFIG BEFORE TREATING THIS AS OPEN OR CLOSED.


-------------------------------------------------------------------------------
H2  No error boundary - a render error falls through to Next's default page
    [LIVE NOW]  [RESILIENCE]
-------------------------------------------------------------------------------

There is no error.js or global-error.js anywhere in src/app. A custom 404 exists
and is correct, but an uncaught exception during render has nothing to catch it,
so a visitor gets the framework's generic error screen with no navigation back
into the site.


-------------------------------------------------------------------------------
H3  No working analytics, and a 404 on every page load
    [LIVE NOW]  [OBSERVABILITY]
-------------------------------------------------------------------------------

@vercel/analytics is mounted in layout.js, but the site runs on a VPS behind
nginx, not on Vercel. The component requests /_vercel/insights/script.js, which
nothing serves.

    Lighthouse errors-in-console:  404  /_vercel/insights/script.js

Confirmed empirically, not inferred. The owner has chosen to keep the component
mounted so it activates on the planned Vercel migration - a defensible call, but
it means there is NO TRAFFIC DATA AT ALL today, and no error tracking of any
kind alongside it.


-------------------------------------------------------------------------------
H4  Contact form delivery has never been confirmed end to end
    [WORKING TREE]  [DELIVERY]
-------------------------------------------------------------------------------

The route is well hardened - server-side validation, HTML-escaped interpolation,
a honeypot, and a 5-per-IP-per-10-minute rate limit returning 429. A live send
returned HTTP 200.

200 proves Resend ACCEPTED the message, not that it ARRIVED. Nobody has
confirmed the business inbox received it.

This is the site's only conversion path. Every enquiry the studio receives
depends on it.

Note: the rate limit is an in-memory Map, correct for THIS deployment only (one
long-lived next start process). On Vercel it degrades to per-instance and is
close to no limit.


-------------------------------------------------------------------------------
H5  No CI, no tests, no linter - the build is the only gate
    [WORKING TREE]  [PROCESS]
-------------------------------------------------------------------------------

There is no .github/workflows, no test files, and no ESLint config. Deployment
is manual: git pull && npm ci && npm run build, then a process restart.

The practical consequence is visible in this audit's own findings: a green build
did not catch a stylesheet referencing a deleted image, or ten detail pages
linking to brand pages that no longer existed.

    ==> A PASSING BUILD MEANS IT COMPILED, NOT THAT IT WORKS.


-------------------------------------------------------------------------------
H6  No "engines" field despite a documented Node floor
    [WORKING TREE]  [DEPLOY]
-------------------------------------------------------------------------------

CLAUDE.md states Node >= 20.9, but package.json declares no engines. Nothing
stops the VPS - or a future Vercel build - from running an older runtime and
failing in a way that points somewhere unhelpful.

M3  A 260 MB .git against a 22 MB public/   [WORKING TREE]  [REPOSITORY]
-------------------------------------------------------------------------------

Image blobs are roughly 95% of history - 24-megapixel originals only ever shrunk
in the working tree, with each re-encoding pass adding a fresh copy. 86 commits,
one committer, nothing pushed since.

A git filter-repo pass would bring it to roughly 25 MB. The precondition that
matters:

    ==> DEPLOYMENT IS "git pull" ON THE VPS, SO AFTER THE FORCE-PUSH THE SERVER
        MUST BE RE-CLONED, NOT PULLED.

Do it before the Sanity migration, not after.

METHOD AND LIMITS
===============================================================================

Every figure here was measured from the repository or from a production server
on port 3100 during this audit. Port 3000 was occupied by a dev server and was
deliberately left untouched.

Lighthouse runs used version 13.4.1 with standard mobile throttling.

ONE CAUTION ON COMPARISONS
Mobile performance measured 92 in this run against 80 recorded earlier. Nothing
in the recent changes can move LCP - that delta is Lighthouse version and
machine load, not an improvement. The two runs are not comparable and should not
be reported as progress.

OUT OF SCOPE
The nginx configuration, TLS setup, DNS, server hardening, backups and process
supervision all live on the VPS and were not inspected. H1 in particular cannot
be closed from inside this repository.
